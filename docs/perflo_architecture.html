Not a CLI tool for the end user, and not a chatbot. A real web app, with the CLI doing quiet work in the basement.

◆ Frontend — required

  • Queue UI — a table: queued, needs approval, auto-paid, quarantined, duplicate. This is the product.
  • Settings page — caps, pause switch, digest hour.
  • The business owner never sees a terminal.

◆ CLI — backend-only

  • perflo recipient pay … is shelled out to by your server code, once a decision is already made.
  • It's plumbing the agent uses to move money — not a surface anyone types into.

03  What the drafted diagram got right — and missed

The one in ARCHITECTURE_AND_PIPELINE_SPEC.md (written by the other session) is structurally correct — same eight stages, same schema. It's a fine reference. It just draws every box in one visual register, which hides the one distinction the whole design leans on.

◆ correct, kept as-is

  • Stage order — ingest → classify → extract → resolve → verify → decide → execute → reconcile is right and matches the PRD exactly.
  • Three-way routing out of the policy gate.
  • Schema in section 4 — the six tables are consistent with FR-23's idempotency key.

◆ missing, added here

  • Actor separation. Original diagram uses one node style for LLM and code alike — visually erases the "LLM never touches money" rule it's supposed to illustrate.
  • The crash-recovery loop. FR-24's "kill -9 between the Perflo call and the record write" case isn't drawn anywhere. Added as the dashed Reconciler → Executor arrow — the mechanism that makes "never pay twice" actually true under a crash, not just in the happy path.
  • Where the owner shows up. Grant approval and new-payee approval happen in a browser, out of band, asynchronously. Drawn as a dashed line so it reads as "not part of the automated loop," which it isn't.

04  Two invariants worth memorizing before you write code

Everything else in the pipeline is negotiable engineering. These two rows in the schema are not — get them wrong and the double-payment tests in the PRD's section 15 fail by construction.

1

Idempotency key — use the PRD's five-part version, not the checkpoints doc's three-part one

Two source docs disagree. The checkpoints doc drops the payment method, currency, and invoice reference — under that version, two genuinely different ₹500 invoices to the same payee in one week collide on the same key.

sha256( gmail_message_id | payee_payment_method_id | normalized_amount | currency | invoice_number_or_content_hash )
2

Exact-match rule — hash the whole payment method, not just the amount

Auto-pay only fires when the sender identity resolves to an approved payee and the extracted payment details hash matches the stored, approved method exactly. One changed character in a UPI ID is a new payment method, not a typo to forgive.

details_hash == sha256(rail | account_or_vpa | ifsc?) → else needs_approval, "changed details"

05  Build order — where you actually are

"Basic and working, then improve it" is the right call — it's literally how the PRD is structured. Level 0 has no LLM in it at all, on purpose: prove the plumbing before trusting anything smart on top of it.
